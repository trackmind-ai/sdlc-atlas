# /index-reqs

Builds or rebuilds `PROJECT_ROOT/.claude/specs/req-index.md` — the flat lookup
table that lets `/work-req` find any REQ-ID in one grep without reading every spec.

Run this:
- Once after your first spec is approved
- After adding a new spec (or run `/approve-spec` which calls it automatically)
- If the index seems stale or a REQ-ID lookup fails

---

## Step 1 — Establish project root

```bash
pwd
```

PROJECT_ROOT = output above.

---

## Step 2 — Scan all approved specs and detect format

```bash
find "PROJECT_ROOT/.claude/specs" -name "*.md" ! -name "req-index.md"
```

For each file found:

1. Read header block (first 15 lines only) — skip if Status is not `APPROVED`
2. Extract `feature/change` slug from header (`**Feature**` + `**Change**`, or `**Spec ID**`, or filename)
3. **Detect format** (one grep each, stop at first match):
   - **Format A**: `grep -m1 "^## 2. Requirements Coverage"` → has REQ-NNN table + AC section
   - **Format B**: `grep -m1 "^| ID | Requirement"` → has FN/NFN table + manual checklist
   - **Format C**: neither above → REQ-IDs cited inline in prose only
4. Extract REQ-IDs and their component files:
   - **Format A**: `grep "^| REQ-[0-9]" file` → each row gives REQ-ID + component
   - **Format B**: `grep "^\| \*\*[FN]" file` → each row gives F-ID/NF-ID + description;
     map component from the row text (file name if mentioned, else the gap/section heading)
   - **Format C**: `grep -o "REQ-[0-9]\+" file | sort -u` → unique REQ-IDs;
     for each, grep the line it appears on to extract the subsection context
5. Determine initial status per REQ-ID:
   - **Format A**: check AC rows — all ✅ → DONE, any ⚠️ → PENDING, any ❌ → MISSING
   - **Format B**: check Manual Testing Checklist — all `- [x]` → DONE,
     any `- [ ]` → PENDING, none found → MISSING
   - **Format C**: check Implementation Tracking table if present; else MISSING

---

## Step 3 — Write req-index.md

Write `PROJECT_ROOT/.claude/specs/req-index.md`:

```markdown
# Requirement Index
<!-- Auto-generated by /index-reqs. Do not edit manually. -->
<!-- Updated: <timestamp> -->

| REQ-ID  | Spec Path                                  | Component/Context             | Format | Status  |
|---------|--------------------------------------------|-------------------------------|--------|---------|
| REQ-001 | landing-page/premium-landing               | Nav.tsx                       | A      | DONE    |
| REQ-028 | landing-page/premium-landing               | Next.js optimization          | A      | PENDING |
| F7      | ui-foundation/navigation-auth-onboarding   | onboarding/page.tsx           | B      | MISSING |
| NF2     | ui-foundation/navigation-auth-onboarding   | All forms                     | B      | DONE    |
| REQ-014 | onboarding/enhanced-post-auth-journey      | 3.4 Backend Onboarding Endpoints | C   | MISSING |
```

Format column values: `A`, `B`, or `C` — tells `/work-req` exactly which
parsing strategy to use without any re-detection cost.

---

## Step 4 — Report

Print:
- Total REQs indexed across all specs
- Count by status: DONE / PENDING / MISSING
- Count by format: A / B / C
- List of specs scanned

Example:
```
✔ req-index.md built
  Specs scanned: 3
  REQs indexed: 83
    DONE:    31
    PENDING:  4
    MISSING: 48
  Formats: A×35  B×14  C×34
```
